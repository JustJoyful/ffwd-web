Launch items for the hosted site (what `pnpm check:release` fails on, and what to do about it)
=================================================================================================

Run `pnpm build` and `pnpm check:release` in the SAME shell: the check reads build/build-info.json, which postbuild.mjs
writes from the VITE_* values the build was made with.

1. The ffmpeg core does not fit on Cloudflare Pages (review B2).
   build/client/ffmpeg/ffmpeg-core.wasm is 32,718,323 bytes (31.2 MiB). Pages serves a file of at most 25 MiB, so a deploy
   of this build fails or loses the file. public/ffmpeg/ is git-ignored and `pnpm build` does not run `pnpm copy-core`,
   so a clean checkout builds with no /ffmpeg files at all. Either way the page then fetches the 404 page as its video
   engine (it now says "ffwd's video engine didn't start", but the tool does not work).
   The core must be served from R2 (or split into files under 25 MiB). The plan in WEB_ARCHITECTURE.md section 8 is R2 on
   an assets host with CORS for the site origin, `Cross-Origin-Resource-Policy: cross-origin`, and a versioned path.
   DONE (2026-11-25, overnight): R2 turned out not to be enabled on the account (it needs the owner in the dashboard), so the
   core is served from the public npm CDN jsDelivr instead, the way the ffmpeg.wasm docs do it:
   VITE_FFMPEG_CORE_BASE=https://cdn.jsdelivr.net/npm/@ffmpeg/core-mt@0.12.10/dist/esm (an immutable versioned URL, CORS *,
   CORP cross-origin). The app checks the sha256 of all three files against fixed values (app/agent/config.js
   FFMPEG_CORE_SHA256, tested against the installed package) before using them, so a changed or tampered file is refused.
   The CSP connect-src names the host and the privacy page says that host sees visitors' IP addresses. Moving to R2 later
   is only a change of VITE_FFMPEG_CORE_BASE (upload the same three files; the hashes still apply).

2. The model manifest (D-053). VITE_MODEL_MANIFEST_URL must be set at build time to the https URL of ffwd-model.json at a
   PINNED Hugging Face tag or 40-hex commit (e.g. https://huggingface.co/<owner>/ffwd-0.6b/resolve/v1.0.0/ffwd-model.json),
   never main/master/latest, and VITE_MODEL_MANIFEST_SHA256 must be the sha256 of that exact file. The app reads the model
   file, size, hash and settings from the manifest and refuses (nothing downloaded) on a protocol_version other than
   protocol/PIN.json's, a min_app_version above APP_VERSION (app/model/config.js), or a prompt/template that differs from the
   app's own. check:release fails on a missing/unpinned URL, a missing hash, or any build stamped by `pnpm release:local`.
   Test the exact package first: `pnpm release:local` (see scripts/serve-release.mjs). The privacy page names the host.

3. Analytics are off unless VITE_POSTHOG_KEY is set at build time. check-release fails if a key is in the build, unless
   FFWD_ANALYTICS_ON=1 is set to say the owner decided to switch it on. (Persistence is "memory": see app/config.js.)

3b. Feedback (opt-in "send this request", separate from analytics). Off unless VITE_FEEDBACK_URL (https) is set at
   build time; then the CSP connect-src gets that host, build-info.json records it, and check:release fails on a
   non-https URL. On the site it is three quiet links, nothing opens by itself: "Not what I meant" in the plan card,
   "Send this request (not your video) to help improve ffwd" under a failed job or an unsupported notice, and "Not what
   you asked?" after Done. The panel shows the exact JSON (kind, request, optional note, plan, failure, app_version,
   model_version); "No thanks" hides every link for the browser session. Backend: workers/feedback (Cloudflare Worker + D1;
   D1 over KV because you can query and count rows with SQL and the free tier is enough). NOT deployed.
   Run these in workers/feedback. Always pass -c wrangler.toml: the site's wrangler.jsonc sits above this folder and
   wrangler would pick it up (d1 then says it cannot find "ffwd-feedback").
     npx wrangler login
     npx wrangler d1 create ffwd-feedback -c wrangler.toml   # paste the printed database_id into wrangler.toml
     npx wrangler d1 execute ffwd-feedback --remote -c wrangler.toml --file=schema.sql
     # edit wrangler.toml: ALLOWED_ORIGIN = "https://<your site origin>"   (comma-separate several)
     npx wrangler deploy -c wrangler.toml          # prints https://ffwd-feedback.<you>.workers.dev
     # build the site with VITE_FEEDBACK_URL=https://ffwd-feedback.<you>.workers.dev
   Already created the table before the note existed? Run once:
     npx wrangler d1 execute ffwd-feedback --remote -c wrangler.toml --command "ALTER TABLE feedback ADD COLUMN note TEXT"
   Limits, all in wrangler.toml (no zone needed, nothing about the client goes into D1):
     - rate limit: [[ratelimits]] binding LIMITER, 5 posts per 60 s per CF-Connecting-IP, then 429. The deploy creates it; the
       namespace_id ("1001") is any string number unique in the account.
     - daily cap: DAILY_CAP = "500" rows per UTC day, then 429 and nothing is stored.
     - retention: a cron trigger ("17 3 * * *", every day 03:17 UTC) runs the Worker's scheduled handler, which deletes
       rows older than RETENTION_DAYS = "90". It starts with the deploy; check Workers > ffwd-feedback > Settings > Triggers.
   Read it (needs wrangler login; the table lists the newest rows, text cut at 70 characters):
     pnpm feedback:read                       last 30 days, newest 50
     pnpm feedback:read --days 7 --kind result_wrong --limit 20
     pnpm feedback:read --counts              counts by kind and failure
   Full text of one row, or remove one row: run wrangler d1 execute ... --command "select * from feedback where id = '<id>'"
   (or the same with delete).
   The privacy page says: request text may be used to improve the model; requests the owner reviews and copies into the
   training set (cleaned of anything personal) are kept there; raw feedback is deleted after 90 days. Keep the cron and
   the page in step: if RETENTION_DAYS changes, change the page (app/routes/privacy.jsx, and its two tests).

4. Placeholder text on the pages ([contact address], [role line], the [Confirm ...] notes, the SITE_URL placeholder).
